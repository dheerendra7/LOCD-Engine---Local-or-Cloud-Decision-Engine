# Deployment

## Render Free profile

The checked-in `render.yaml` describes one **Free** Node web service named `locd-engine`:

- Build: `npm ci`; start: `npm start`; runtime: Node 24.21.0 via `.node-version`.
- Health check: `/ready`; the process listens on Render's `PORT` and binds to `0.0.0.0`. Automatic deploys wait for linked Git checks to pass.
- Compute: Free plan, Singapore region, one instance.
- No persistent disk and no paid database are provisioned.
- Runtime profile: `LOCD_DEPLOYMENT_PROFILE=free-preview`, surfaced by the authenticated status API so the dashboard can show the correct operating constraints.
- Security defaults: API authentication key generated by Render, in-process API rate limiting enabled at 60 requests/minute, strict durable-state production gate disabled because the Free filesystem is ephemeral.
- Live provider execution remains disabled (`LOCD_EXECUTION_ENABLED=false`).

### Frontend + API topology

This is a single-origin full-stack deployment. The API process serves `apps/web/index.html`, `apps/web/styles.css` and `apps/web/app.js` at `/`, `/styles.css` and `/app.js`; the same process handles the dashboard's `/v1/*` requests. No separate frontend host, public API URL or permissive CORS configuration is required.

After the first Blueprint deploy, retrieve the generated `LOCD_API_KEY` from the Render service's Environment page and paste it into **System & access** in the dashboard. The overview displays an authentication setup notice when API calls return 401 and a scope warning when they return 403. The browser keeps the key in page memory only; do not place it in source code, a checked-in config file or a public frontend variable.

### Free-tier data and availability limits

Render Free services spin down after 15 minutes without inbound traffic and can take about a minute to wake. They have an ephemeral filesystem: in-process telemetry, policies, target registrations, coordination and other local file state are not durable and can reset on restart, deploy or spin-down. This deployment is therefore a **free public preview/evaluation environment**, not a durable production control plane. Do not store customer-critical data or rely on saved targets/policies/history here.

No SQLite file path or target/policy file path is configured in this profile, so the application uses its in-memory defaults. Live provider execution is disabled to avoid presenting ephemeral single-process coordination as durable execution safety. To move beyond preview use, attach a separately managed durable database/storage service and migrate the state backends before enabling execution or promising persistence/HA.

The Free plan has monthly usage limits and may be suspended after the included free instance hours are exhausted. See https://render.com/docs/free.

## CI runner reproducibility

The CI workflow pins GitHub-hosted Linux jobs to `ubuntu-24.04` instead of `ubuntu-latest`, keeping the test environment stable until the project intentionally upgrades it.

## Runtime version

The repository pins Render's Node.js runtime to `24.21.0` through `.node-version`. The package engine range is bounded to Node.js `>=22.16.0 <25`, and the Docker image is pinned to `node:24.21.0-alpine3.24`. CI continues to exercise the supported 22.x and 24.x lines.

Keeping an upper bound prevents an unrelated future Node major from silently changing deployment behavior.

## Container deployment

The Docker image runs the application as the unprivileged `node` user. The Compose configuration mounts `/data` as a named persistent volume and configures `LOCD_STATE_DB_FILE=/data/locd.db`, so the reference container deployment keeps telemetry, coordination and policy state across container restarts.

For production, place a TLS-terminating reverse proxy or load balancer in front of the container and use managed persistent storage with backup/restore controls. The image healthcheck remains a local liveness check against `/health`.

## Multi-tenant deployment

Bind each scoped API credential to a tenant using its tenantId in LOCD_API_KEYS_JSON. Keep tenant identifiers stable because they become part of target, telemetry, calibration, idempotency and rate-limit namespaces.

LOCD_TARGETS_FILE now supports a versioned tenant-aware format:

    {
      "version": 1,
      "tenants": {
        "acme": [ ... ],
        "beta": [ ... ]
      }
    }

A legacy target array is still loaded into the default tenant.

The tenant model is an application-level isolation boundary. For strong production isolation, the state service/database and operational credentials must remain inside the same trusted deployment boundary.

## Policy control plane

Set LOCD_POLICIES_FILE to persist tenant-scoped custom policies and their bounded version history. Built-in profiles remain read-only. Policy mutations require an admin credential and are resolved server-side during /v1/decide.

The file is written atomically. On hosted platforms with ephemeral filesystems, use durable storage or a managed configuration backend before relying on restart persistence.

For multi-instance deployments, the internal State Service also provides tenant-scoped transactional policy storage when LOCD_STATE_SERVICE_URL is configured. LOCD_POLICIES_FILE remains the local/file-backed fallback when shared state is not enabled.

## Strict production safety mode

Set `LOCD_PRODUCTION_STRICT=true` for hosted deployments that provide durable telemetry and policy backends. Strict mode fails closed at startup when core control-plane safety requirements are missing.

## Remaining production operations

The Free profile is a preview baseline, not a substitute for production operations. Before exposing it to real workloads:

- Configure a custom domain and verify HTTPS, DNS and rollback behavior.
- Set up uptime and error-rate monitoring.
- Configure a durable database/storage backend and backup/restore controls.
- Add only the provider adapters and credentials that the deployment actually needs; keep credentials in service secrets, not in provider JSON or browser code.
- Load-test the API and dashboard with the intended workload and request volume.
- Keep live execution disabled until durable shared coordination, provider configuration, authorization scopes, target isolation, idempotency and cancellation behavior have been verified in staging.
- Do not claim multi-instance availability, durable telemetry, a 30-day SLO or a permanent compliance audit trail from the in-memory Free deployment.

## Persistent target registry

Set:

    LOCD_TARGETS_FILE=/var/lib/locd/targets.json

The server restores targets from this JSON file at startup and writes the file after target registration/removal. On managed platforms with ephemeral filesystems, use durable storage or a database-backed registry before depending on restart durability.

## HTTP resource guards

The API applies explicit Node.js HTTP resource limits so incomplete requests and idle keep-alive connections cannot consume server resources indefinitely.

- `LOCD_REQUEST_TIMEOUT_MS`: maximum time to receive the full request (default 30 seconds).
- `LOCD_HEADERS_TIMEOUT_MS`: maximum time to receive HTTP headers (default 10 seconds). It must not exceed the request timeout.
- `LOCD_KEEP_ALIVE_TIMEOUT_MS`: idle keep-alive timeout (default 5 seconds).
- `LOCD_MAX_REQUESTS_PER_SOCKET`: maximum requests served per connection; `0` means unlimited.

Tune these with the deployment proxy/load balancer in mind.

## API hardening configuration

Use LOCD_MAX_BODY_BYTES to cap JSON request size.

Use `LOCD_RATE_LIMIT_RPM` to enable an in-process `/v1` rate limit. Only enable `LOCD_TRUST_PROXY=true` when the API cannot be reached directly from untrusted networks and a trusted ingress proxy appends or overwrites `X-Forwarded-For`. Configure `LOCD_TRUST_PROXY_HOPS` to the exact number of trusted proxy hops (default `1`). LOCD selects the client address by counting from the right edge of the forwarding chain, so untrusted entries on the left do not override the address appended by the trusted ingress. If the selected entry is not a valid IP address or the chain is shorter than configured, LOCD falls back to the socket peer address. Incorrect hop counts may group users behind a proxy or select the wrong address; do not turn on proxy trust without matching the real network topology.

Rate limiting is intentionally local to a process; distributed deployments need a shared limiter for a global quota.

Live execution also requires the API rate limiter to be enabled. Set `LOCD_RATE_LIMIT_RPM` to a positive value (or supply an enabled custom limiter) before enabling live execution; otherwise `POST /v1/execute` returns HTTP 503 without invoking a provider.

Live execution additionally requires `LOCD_EXECUTION_PLAN_SECRET` with at least 32 bytes. Set `LOCD_EXECUTION_PLAN_TTL_MS` to control the signed-plan lifetime (default 600 seconds, maximum 15 minutes). Use the same secret on every API instance behind the same load balancer. In strict production mode, enabling live execution without this secret or without shared coordination for single-use plan claims fails startup. A process-local coordination store provides only per-process replay protection; use the shared backend for a multi-instance deployment.

The API issues signed authorizations only for valid plans evaluated against the authenticated tenant's registered targets. Request-scoped target arrays are simulation inputs only. At execution time LOCD verifies the tenant-bound signature and expiry, reloads current targets, and re-runs policy/circuit validation before invoking any adapter.

## Provider circuit breaker

Registered targets use a tenant-scoped circuit breaker. Provider execution failures and automatic/manual health-probe failures contribute to the configured failure threshold. Live execution deadlines and HTTP client disconnects are propagated as AbortSignals to provider adapters. Cancellation is best effort: a remote provider may continue processing a request it accepted before the abort.

## HTTP security headers

The API and internal State Service add `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer` to responses. Browser-served console assets additionally receive a restrictive Content Security Policy.

## Structured logs

LOCD emits structured JSON request lifecycle events to stdout. Use LOCD_LOG_LEVEL to control verbosity. The logger redacts credentials and other sensitive fields and does not log request bodies.

## Health and shutdown

Use `GET /health` for liveness and `GET /ready` for readiness. Both are intentionally public so load balancers and platform health checks can call them without application credentials.

The API and internal State Service allow `LOCD_SHUTDOWN_TIMEOUT_MS` (default 10 seconds) for graceful termination. During the grace window, in-flight requests can complete normally; after the deadline, established HTTP connections are force-closed so process shutdown cannot hang indefinitely.

The application handles SIGTERM/SIGINT and stops the probe scheduler before closing the HTTP listener.

## SQLite state backend

Set LOCD_STATE_DB_FILE to a persistent SQLite database path to enable durable decision telemetry and shared coordination from one LOCD host. The SQLite path uses Node's built-in node:sqlite, WAL mode and a busy timeout for concurrent writers. It is appropriate for a single host or deployment that provides a reliable shared filesystem. It is not a network database for unrelated hosts.

## SQLite backup and recovery

Use `npm run state:backup -- <source.db> <destination.db>` or the equivalent CLI command to create a native online SQLite backup. Native SQLite online backup support requires Node.js 22.16+.

## Multi-instance shared state

For multiple API instances, set LOCD_STATE_SERVICE_URL and LOCD_STATE_SERVICE_API_KEY to share telemetry and coordination through the reference network state service. Use LOCD_COORDINATION_URL instead when you need shared rate limiting/idempotency without moving decision telemetry off the API process.
